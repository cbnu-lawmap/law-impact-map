# Agentic RAG: 근거가 부족하면 다음 출처를 찾는 검토 에이전트

검토 에이전트(`server/api/agent.js`)에 방식(`mode`) 두 가지를 더했다. 기본 방식(`agent`)은 그대로다.

| mode | 이름 | 찾는 출처 | 모델 호출 | 하는 일 |
|---|---|---|---|---|
| `agent` (기본값) | 에이전트 (도구 고르기) | 요약(제안이유) 한 번 | 도구 고르기 반복 + 기준 뽑기 + 초안 | 지금까지와 같음 |
| `rag1` | 1회 RAG (13주차 질의 도우미식) | 요약 한 번 | 기준 뽑기 한 번 | 요약을 찾고, 모델이 기준을 뽑고, 코드가 원문 대조·평가·판정. 초안은 정해진 틀 문장 |
| `agentic` | Agentic RAG | 요약 → 법안 원문 → 검토보고서 → 비슷한 법안 규칙 | 도구 고르기 반복 + 출처마다 기준 뽑기 + 초안 | 출처를 찾을 때마다 코드가 근거를 평가하고, 부족하면 다음 출처를 찾는다 (재검색 최대 3번) |

코드: `server/lib/sources.js` (출처 찾기, 근거 평가, 비슷한 법안 규칙), `server/lib/agentic.js` (`rag1`, `agentic` 실행), 시험 `server/test/agentic-rag.js`.

## 1. 흐름

```
1회 RAG      요약 찾기 → 기준 뽑기(모델 1번) → 근거 평가(코드) → 판정 → 초안
Agentic RAG  요약 찾기 → 근거 평가(코드) ─ 충분 ──────────────────────────→ 판정 → 초안
                              └ 부족 → 법안 원문 → 근거 평가 ─ 충분 ─────→ 판정 → 초안
                                              └ 부족 → 검토보고서 → 근거 평가 ─ 충분 → 판정 → 초안
                                                             └ 부족 → 비슷한 법안 규칙 (후보만) → 판정 → 초안
```

- 모델이 고르는 도구는 `search_sources(no, source)`, `judge_buildings(rule)`, `draft_review(no)` 셋이다.
- `search_sources` 를 부를 때마다 서버 코드가 `evaluate_evidence`(근거 평가)를 바로 돌려 단계 기록에 남긴다 (`auto: true`, 화면에는 「코드 자동」). 모델이 평가를 정하지 않는다.
- 평가 결과에 따라 서버가 다음 할 일(`next`)을 정해 도구 결과에 넣는다. 단계 기록에는 「평가 결과: … → 다음 출처 … 선택: (이유)」가 남는다.
- 서버가 막는 것: 순서를 건너뛴 출처(「순서상 다음 출처는 bill_text 입니다」), 이미 찾은 출처, 근거가 충분한데 더 찾기, 재검색 3번 초과(「재검색은 3번까지입니다」). 거절도 한 단계로 센다 (최대 8단계).
- 모델이 중간에 멈추거나 단계·토큰 제한에 걸리면, 서버가 같은 순서로 남은 출처를 정규식 추출로만 찾고(토큰을 쓰지 않음) 판정·초안을 마무리한다 (「서버 마무리」).

## 2. 출처 (`search_sources`)

| source | 글 | 어디서 |
|---|---|---|
| `summary` | 제안이유 전문 (없으면 300자 요약) | `web/data/summaries.json` |
| `bill_text` | 법안 원문의 **개정 부분**만 (개정문 안의 새 글. 제안이유·정의 조문·부칙·신구조문대비표 뺌, `criteria.js` 의 `amendedText`) | `web/data/bill_docs.json` |
| `review_report` | 검토보고서에서 건물 기준 낱말(연면적·층·용도·위임 문구 등)이 든 문장, 3,000자까지 | `web/data/bill_docs.json` |
| `similar_rules` | 제안이유가 비슷한 시범 법안 3건의 규칙 | `demo_rules.json` + TF-IDF (측정 결과가 결합이면 TF-IDF·pgvector RRF) |

- 자료가 없으면 `found: false`, 글은 「없음」이다. 출처 없음도 재검색 한 번으로 센다.
- `web/data/bill_docs.json` 은 `node server/scripts/build-bill-docs.js` 가 `data/bill_docs/*.txt` 에서 만든다 (36건, 약 85KB). 사람 이름이 나올 수 있는 문장(의원·전문위원·조사관·위원장·대표발의)은 싣지 않는다. `npm test` 가 파일이 최신인지 확인한다. 원문·검토보고서는 시범 26건과 곧 통과 후보 10건만 있고, 2207658(나중에 넣은 시범 법안)은 없다.
- `similar_rules` 는 `createSimilarRules(D)` 가 만든 함수 `similarRules(no, k)` 하나로 되어 있다 (문자 2~3글자 TF-IDF, 코사인 유사도). agentic 요청에서는 `api/agent.js` 의 `withVectorRules` 가 비슷한 법안 찾기(`server/lib/similar.js`)와 같은 방법을 따른다: 기본 방법이 `tfidf` 면 이 TF-IDF 그대로, `hybrid` 면 시범 법안 중 pgvector 상위 20 과 TF-IDF 순위를 RRF 로 합친 3건 (같은 모양 `[{no, title, score, rule, label}]`).
- 기본 방법은 손이 아니라 측정으로 정한다. `collect/compare_similar.py` (GitHub Actions `embed-bills.yml`) 가 같은 법률 법안 691건에서 잰 값 ([similar_compare.md](similar_compare.md)):

  | 방법 | top-3 적중률 | top-1 적중률 |
  | :--- | ---: | ---: |
  | 단어 유사도(TF-IDF) | 88.6% | 73.2% |
  | 의미 검색(pgvector 임베딩) | 70.6% | 50.7% |
  | 하이브리드: 단어 + 의미 결합(RRF, k=60) | 83.8% | 67.4% |

  규칙 「결합 top-3 ≥ TF-IDF top-3 이면 hybrid」 에 따라 지금 기본 방법은 `tfidf` 다 (`web/data/similar_method.json`, 환경변수 `SIMILAR_METHOD` 로 바꿀 수 있음).
- 비슷한 법안의 규칙은 언제나 **「후보 규칙, 사람 확인 필요」** 표시만 붙여 보여 준다. 판정 규칙에 넣지 않고, 모델이 `judge_buildings` 에 넘기면 「후보 규칙은 사람 확인 전이라 판정에 쓰지 않습니다」로 거절한다.

## 3. 근거 평가 규칙 (`evaluate_evidence`, 코드만)

기준(용도·연면적·층수·세대수·사용승인)마다 출처 하나의 글로 셋 중 하나로 나눈다. 모델 결과는 후보일 뿐이고, 상태는 아래 코드 규칙으로만 정한다.

| 상태 | 조건 |
|---|---|
| 판정에 충분 | `criteria.verify` 통과: 근거 문구가 출처 글에 그대로 있음(원문 대조), 연면적은 수치와 면적 단위(㎡·제곱미터), 층수는 수치와 「층」, 사용승인은 「N년」, 용도는 그 용도의 시설 이름이 근거 문구에 있음 |
| 위임 확인 | 수치는 없지만 그 기준을 대통령령·부령·조례에 넘긴 위임 문구가 출처 글에 있음 (`criteria.findDelegation`). 용도는 「용도」, 연면적은 「규모·면적」, 층수는 「층」이 위임 문구에 있어야 함 |
| 부족 | 기준 낱말(예: 「일정 규모 이상」, 「연면적」, 「층수」)은 있지만 위 둘에 못 미침. 버린 이유(근거 문구가 원문에 없음, 수치가 근거에 없음, 단위 없음 등)를 함께 적음 |

개정문 여부:

- `summary`, `review_report` 는 문장을 현행·개정·통계·배경·기타로 나눠, 현행·통계·배경 문장의 수치(연면적·층수·세대수·사용승인)는 판정 규칙에 넣지 않는다. 현행 문장 수치는 `extraction.current` 로 따로 보인다 (규칙: [bldg_register_analysis.md 「현행·개정 문장 구분」](bldg_register_analysis.md#현행개정-문장-구분)). 현행 문장에만 나온 기준은 「부족」(버린 이유 "현행 기준 설명 문장")으로 남아 다음 출처(개정 조문)를 찾는다.

- `bill_text` 는 개정 부분 글만 싣기 때문에, 여기서 통과한 근거는 개정 조문에서 나온 것이다.
- `review_report` 는 근거 문구에 개정 내용을 말하는 표시(개정안, 안 제N조, 신설, …하려는, …하도록 함)가 있어야 받는다. 없으면 「개정 내용을 말하는 문장이 아님 (현행법·참고 설명일 수 있음)」으로 버린다. 검토보고서에는 현행 시행령 표가 많이 섞여 있어서다.
- `bill_text`, `review_report` 에서 같은 기준(예: 연면적 이상)의 수치가 둘 이상 다르게 나오면 「각 호 중 하나의 조건」일 수 있어 그 기준은 버린다 (`extractFromDoc` 와 같은 규칙).

기준 모으기 (`mergeEvaluations`):

- 따라갈 기준 목록은 요약에서 말한 기준이다. 요약에 기준 낱말이 하나도 없으면 기준을 처음 말한 출처의 기준이다.
- 기준마다 가장 좋은 상태(판정에 충분 > 위임 확인 > 부족)를 쓰고, 판정 규칙에는 처음 「판정에 충분」이 된 출처의 값을 넣는다. 문서에서 원문 대조를 통과한 위임 기준도 넣는다.
- 요약에서 부족(또는 언급 없음, 위임 확인)이던 기준이 나중 출처에서 「판정에 충분」이 되면 `revived`(재검색으로 확인)에 넣는다.
- 나중 출처에서 처음 나온 기준은 `extra_criteria`(요약에 없던 기준, 참고만)로만 보이고 판정 규칙에 넣지 않는다. 검토보고서에는 다른 용도·수치가 많이 나와 판정이 넓어지지 않게 하려는 것이다.
- 더 찾는 조건: 기준이 하나도 없거나 「부족」인 기준이 있을 때. 「위임 확인」은 더 찾지 않는다 (시행령이 나와야 정해짐).

판정은 지금과 같다: 모은 규칙이 건물을 가를 수 있으면 그 규칙, 아니면 판정 시범 규칙, 그것도 없으면 판정 보류(위임이면 「판정 보류: 시행령(대통령령 등)에 위임돼 기준 확정 전」, 아니면 「판정 보류: 찾아본 출처에서 판정 기준을 찾지 못함」).

## 4. 토큰과 모델에게 주는 글

- 한 번 실행 토큰 상한 12,000, 단계 최대 8번, 호출마다 `max_tokens` 는 `agent` 와 같다. 다음 호출의 최대 출력까지 더해 상한을 넘을 것 같으면 부르지 않는다.
- 기준 뽑기(모델)는 출처 글을 3,500자까지만 넣는다.
- 도구 결과로 대화에 다시 실리는 것은 짧은 요약뿐이다: 출처 이름, 찾았는지, 평가 한 줄(「용도 판정에 충분 (요약), 연면적 부족」), 다음 할 일. 출처 글 전체는 대화에 넣지 않는다 (1,200자 이하).

## 5. API

`POST /api/agent` 본문 `{"bill": "2204029", "mode": "agentic"}` (또는 주소 `?mode=agentic`). `mode` 를 빼면 `agent` 로 예전과 같다. 모르는 값은 400.

응답 (세 방식 공통으로 더한 칸):

| 칸 | 뜻 |
|---|---|
| `mode` | `agent` / `rag1` / `agentic` |
| `steps`, `step_count` | 단계 기록과 그 수 (코드 자동 평가·서버 마무리 단계 포함) |
| `tokens`, `limits` | 쓴 토큰, `{max_steps, token_cap, max_researches, stopped}` |
| `evaluation` | 기준별 `{attr, status, value, quote, source, history[], revived_by}` |
| `sources_used` | 찾은 출처 `{source, source_ko, found}` (순서대로) |
| `revived` | 재검색으로 살린 기준 `{attr, from, by, by_ko}` |
| `extraction.rule` | 원문 대조를 통과해 모은 규칙 (시범 규칙으로 대신하기 전) |
| `candidates` | `agentic` 의 비슷한 법안 후보 `{no, title, score, rule, label: "후보 규칙, 사람 확인 필요"}` |
| `researches`, `search_stop` | 재검색 횟수, 찾기를 멈춘 이유 |

`agent` 방식 응답에도 `mode`, `step_count`, `evaluation`(요약 한 출처), `sources_used`, `revived: []` 를 더했다. 나머지 칸과 단계 순서는 바뀌지 않는다.

행정 화면(`web/admin.js`) 법안 상세의 「방식」 고르기에서 세 방식을 고를 수 있고, 결과 카드에 1회 RAG 와 Agentic RAG 흐름 그림(지나온 단계는 색, 마지막 단계는 굵은 테두리, 찾지 않은 출처는 점선), 기준별 근거 평가 표, 후보 규칙이 나온다.

## 6. 세 방식 비교

```
node server/scripts/compare-rag.js            # 배포 서버, 시범 27건 x 3방식, 호출 사이 13초 (약 18분)
node server/scripts/compare-rag.js --bills 26 # 처음 시범 26건만 (2207658 뺌)
```

- 대상은 기본으로 `demo_rules.json` 의 시범 **27건** 모두다 (`--bills 26` 이면 처음 26건).
- 서버는 IP당 1분 5회만 받으므로 호출 사이에 13초 쉰다. Vercel 환경변수 `AGENT_COMPARE_TOKEN`(16자 이상)을 넣고 같은 값을 실행 환경변수로 주면 `x-compare-token` 헤더로 호출 수 제한·사이트 확인·10분 저장을 건너뛴다. 환경변수가 비어 있으면 이 길은 닫혀 있다. 열쇠는 코드와 결과 파일에 남기지 않는다.
- `--local` 은 서버 없이 핸들러를 직접 부른다 (`OPENAI_API_KEY` 필요. `AGENT_MOCK=1` 이면 가짜 모델로 흐름만 확인).
- 결과: `data/rag_compare.csv` (법안 x 방식 한 줄), 표준 출력에 아래 표.

지표:

- 원문 대조 통과 기준 수: `extraction.rule` 의 기준 수 합 (용도·연면적·층수·사용승인·위임)
- 시범 규칙 일치 수: `extraction.rule` 이 시범 규칙과 똑같은 법안 수 (시범 규칙으로 대신 판정한 것은 세지 않음)
- 평균 토큰, 평균 단계 수
- 재검색으로 살린 법안: 요약에서 부족했던 기준이 나중 출처에서 판정에 충분이 된 법안

| 방식 | 성공 | 원문 대조 통과 기준 수 | 시범 규칙 일치 수 | 평균 토큰 | 평균 단계 수 | 재검색으로 살린 법안 |
|---|---:|---:|---:|---:|---:|---:|
| agent (도구 고르기) | 26/27 | 20 | 3 | 9,316 | 7.2 | - |
| rag1 (1회 RAG) | 27/27 | 21 | 5 | 958 | 5.0 | - |
| agentic (Agentic RAG) | 27/27 | 29 | 6 | 7,452 | 8.0 | 5 |

2026-11-23 배포 서버(gpt-4o-mini)에서 시범 27건 × 3방식을 `node server/scripts/compare-rag.js` 로 잰 값 (법안별 결과 `data/rag_compare.csv`). agent 1건(2220379)은 네트워크 오류로 실패해 26건 평균. 모델 출력은 실행마다 조금 달라질 수 있다. 시범 규칙 일치 수는 사람이 고른 시범 규칙과 똑같은 법안 수라 정답률이 아니다.
